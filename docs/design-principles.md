# SysArmor 设计原则

本文定义 SysArmor 的架构总纲。它解释系统为什么这样设计，并约束产品、架构、接口、策略和测试的后续表达。组件、协议和数据库是实现手段，不是设计原则本身。

## 核心判断

主机安全不是一次性识别问题，而是攻击者与防御系统围绕可见性、成本、时机和处置权限进行的持续博弈。

有效系统必须同时满足三个条件：能够随对抗变化调整策略；能够在行为粒度与资源成本之间保持可测量的平衡；能够让端侧及时判断与云侧全局关联相互增强。SysArmor 将它们概括为动态博弈、效能平衡和端云协同。

```text
动态博弈决定系统如何变化
效能平衡决定系统观察和传输多少
端云协同决定计算、数据和决策放在哪里
```

三者不是独立功能。控制平面根据端云反馈调整策略，策略改变采集、检测、传输和响应行为，新的 Event、Signal 与 Evidence 又成为下一轮调整的依据。

## 统一数据语义

Event、Signal、Stage、DetectorKind、Where、Evidence 和 Incident 的正式定义见[安全数据模型](concepts/security-data-model.md)。本原则只讨论为什么需要这些分层，不在此复制概念合同。

这组语义让系统在保留事实、检测发现、可复核依据和安全分析报告之间建立明确边界。由既有 Signal 派生的新 Signal 必须保留稳定引用链和生成规则，使重试、重算和调查能够追踪来源。

## 原则一：动态博弈

### 为什么必须动态

攻击者会观察防御行为并改变载荷、执行路径、时间窗口和资源使用方式。固定采集面、固定规则和固定响应动作只能描述已知环境，无法长期应对“机-机对抗”。因此，安全系统必须把策略调整能力放进架构，而不是依赖重新编译或人工逐机修改配置。

### 四个可调层面

目标架构中的统一策略必须能够从控制平面调整四个层面：

| 层面 | 控制内容 | 典型问题 |
|---|---|---|
| Collection | 行为类型、选择器、作用域、采集深度和资源预算 | 当前需要观察什么，粒度应有多深 |
| Detection | 本地规则、内容集合、阈值、关联条件和收敛逻辑 | 哪些行为组合值得形成 Signal 或 Incident |
| Telemetry | 上传范围、批次、压缩、保留、速率和优先级 | 哪些信息离开端点，何时以及以多大成本上传 |
| Response | 允许动作、作用域、审批、观察模式和执行限制 | 系统可以做什么，哪些动作必须由人确认 |

这四部分必须属于同一策略版本和同一审计链，避免采集、检测、上传和响应各自变化后形成无法解释的有效状态。

### 控制闭环

```text
环境与威胁变化
  -> 控制平面形成策略意图
  -> 校验、解释、编译和资源预算检查
  -> 下发到指定 tenant、Agent 或运行作用域
  -> Agent 原子应用并报告有效版本
  -> health、Event、Signal、Evidence 和资源指标反馈
  -> 人工或 Agentic 分析生成下一轮策略建议
```

### 当前基础与目标能力

当前统一 Endpoint Policy 已包含 collection、detection、telemetry、response 四个必填部分。Manager 可以保存、发布、分配策略并生成下发命令；Agent 会先解析、展开引用、编译和校验完整策略，再应用 collection、持久化策略并切换 detection、telemetry 和 response 有效状态，同时返回确认信息。有效策略、能力和健康状态均可查询。但“进入同一策略”不等于四层已经具备相同成熟度：

| 层面 | 当前已具备 | 当前边界 | 目标能力 |
|---|---|---|---|
| Collection | 选择行为类型、结构化 selector、运行 scope 和 `observe_only`；展开部分内容引用；报告 sensor 下推、Agent 侧过滤和不支持的 selector；运行时应用失败时保留原有效配置 | 没有风险触发的临时加深窗口、到期自动恢复，也没有把 CPU、事件率和丢弃预算统一纳入策略闭环 | 按风险和资源状态临时扩大采集面，在明确作用域、预算和期限内自动恢复 |
| Detection | 端侧 ruleset、rule override、mode、context/IOC 引用和 CEP 资源上限；策略或内容变化时重建检测引擎，失败不替换原引擎；云侧可按有效策略选择 Cloud Rule 和收敛参数 | 未解析的 ruleset、context 或 IOC 引用可能被跳过或降级；Cloud Signal 尚未完整填充规则、上游 Event/Signal 引用、严重度、置信度和模式字段；当前云侧关联不等于完整因果推理 | 完整派生引用链、严格内容依赖、更多可配置关联方法，以及受约束的 Agentic 规则建议与调优 |
| Telemetry | 热更新 `max_batch_items`、`max_batch_bytes` 和 `flush_interval`；具备有界队列、按确认推进、失败重试和 drop/retry 指标 | 不能按 Event/Signal 类型选择上传范围，也没有价值优先级、动态速率、差异化保留或风险驱动的传输预算 | 按数据价值和调查状态调整上传范围、优先级、速率、保留与回压策略 |
| Response | 策略可限制 action、mode、审批人数与角色以及破坏性动作；Manager 校验 scope 和有效策略，记录命令、审批、拒绝与回执；Agent 可接收命令并返回执行状态 | 默认模式是 `observe`；当前 Tetragon 后端对 `enforce` 返回 unsupported，真实隔离或阻断尚未实现；action 命名与 capability 宣告仍需统一；Evidence pullback 只有控制通道和实体占位结果 | 可验证、可撤销或有超时的真实处置动作，统一 action/capability 契约，以及受策略约束的原始材料采集 |

跨层仍有两个共同边界：Manager 和 Agent 当前不会强制拒绝较低策略版本，版本单调性由调用方保证；策略也没有统一的生效期限、自动回滚和风险窗口恢复机制。Agentic 能力必须复用现有的分配、校验、预算、审批、确认和审计闭环，不能绕过这些约束直接修改端点状态。

### 安全不变量

- 策略必须先校验和编译，成功后才能替换有效版本。
- 策略作用域必须绑定 tenant、Agent 和运行目标，不能跨边界扩散。
- 高风险响应必须受到允许动作、审批、最小作用域和审计约束。策略变更必须可回滚；可逆响应应支持撤销或超时；不可逆响应必须具备更严格审批和补偿或恢复预案。
- Agentic 系统只能在授权边界内提出或执行策略，不能绕过控制平面。
- 每次策略变化都必须能够回答谁在何时改变了什么，以及端点实际应用了哪个版本。

## 原则二：效能平衡

### 核心矛盾

主机事件采集的核心矛盾是粒度与性能。采集过少会丢失因果和上下文，采集过多会消耗 CPU、内存、磁盘和网络，并增加云侧检索与关联成本。正确目标不是最大化事件数量，而是在给定资源预算下最大化安全信息价值。

### 分层压缩

SysArmor 通过 Event、Signal、Evidence 和 Incident 建立逐层压缩：

```text
大量 Event
  -> 端侧规范化、选择和局部关联
较少 Signal + 轻量 Evidence 引用
  -> 云侧跨时间、跨批次和跨实体关联
Incident + 初始 Evidence 子图
  -> 当前：生成初始 Evidence 子图
  -> 目标：按需回拉原始材料，补充调查证据
```

Signal 是这一平衡的关键。完整 Signal 语义应保留行为、实体、时间、lineage、Evidence 引用和策略版本，使平台不必默认上传或长期保留所有原始事件，也不会只收到缺少依据的传统告警。当前不同 Signal 生成器的字段完整度并不一致，Cloud Signal 的来源引用仍需补齐。

Evidence 分为三个层次：Signal 应保留轻量事件、实体和上游 Signal 引用；Incident 构建时根据贡献 Signal 生成初始 Evidence 子图；目标能力是在高风险调查时按需受控回拉原始材料。当前 pullback 只有请求、下发、回传控制通道，Agent 根据 `target` 返回实体占位子图，不读取 Event、`raw_ref` 或原始文件。该结果只能验证控制链路，不能证明原始材料已经回拉。按需回拉不是 Incident 拥有 Evidence 的前提。

### 可测量预算

效能平衡必须由指标约束，而不是主观描述。每种策略至少应说明：

- Agent 与 sensor 的 CPU、RSS 和启动峰值；
- Event 与 Signal 的产生速率、队列长度和上传速率；
- 本地存储上限、保留时间、淘汰和丢弃计数；
- Signal 压缩比、Evidence 回拉量和云侧查询成本；
- 在恶意与良性场景中的必要结果、误报边界和缺失原因。

丢弃、解析错误和预算超限必须显式报告，不能被当作成功处理。性能测试、检测效果测试和产品链路测试回答不同问题，不能互相替代。

### 自适应深度

目标架构应允许采集深度随风险变化：低风险时维持小而稳定的常开面；出现高价值 Signal 后，在授权范围和时间窗口内提高采集粒度、Evidence 保留或响应强度；风险消退后回到常态预算。这是动态博弈与效能平衡的交汇点。当前实现具备策略基础和 Evidence pullback 控制通道，但尚未完成真实原始材料回拉、自动临时加深和自动恢复。

## 原则三：端云协同

### 端侧职责

端侧靠近真实行为，负责低延迟、与网络状态无关的能力：

- 管理 sensor 生命周期和采集作用域；
- 规范化 Event，过滤不符合策略或低价值的事件；
- 运行低延迟检测并产生 Endpoint Signal；
- 在容量边界内保存 Event、Signal、策略和上传进度；
- 断网或未注册时继续工作；
- 执行经过授权的响应并返回确认。

端侧过滤不是静默丢弃。过滤规则、预算、丢弃量和原因必须可解释、可观测。

### 云侧职责

云侧拥有更长时间窗口和更大关联范围，负责：

- 可靠接入与 tenant、Agent 身份校验；
- 合并当前批次与限定作用域内的历史 Event 和 Signal；
- 构建实体关系与 Evidence 子图，运行 K-hop、最短路径等图算法；
- 生成 Cloud Signal 和稳定 Incident 投影；
- 支持集中查询、调查、策略管理、审计和响应编排。

当前图能力应与完整威胁溯源区分。实体图、Evidence 子图、K-hop 和最短路径是已具备的算法基础；完整因果路径恢复、候选路径排序、攻击阶段推理和自然语言根因解释仍需单独验证。

### 协同边界

- 端点安全首先必须在端点成立，云侧不可用不能使本地采集和检测停止。
- 端侧只上传策略允许的数据，注册不会创建第二条采集路径。
- 云侧关联必须受 tenant、分析作用域和时间窗口约束，不能把无关行为拼接成攻击链。
- 数据批次、Signal、Evidence 和 Incident 使用稳定身份，使重试与重算收敛到同一逻辑结果。
- 云侧可以增强端侧策略，但必须通过版本化控制平面完成，不能绕过 Agent 的校验、预算和授权边界。

## 三项原则如何共同工作

以目标闭环中的一次可疑外联为例：端侧在常态预算下采集进程与网络行为，形成包含实体和 lineage 的 Signal；云侧将其与历史文件落地 Signal 放入同一作用域，构建 Evidence 子图并形成 Incident；控制平面根据风险和资源状态建议临时扩大相关进程的采集深度或请求原始材料；Agent 校验并应用策略，在窗口结束后恢复常态配置。当前系统已具备本地 Signal、云侧关联、初始 Evidence 子图和策略控制基础；原始材料回拉、自动临时加深和自动恢复仍是目标能力。

这个过程同时体现：策略随对抗变化，数据量受预算约束，端侧及时判断与云侧图关联互相增强。

## 架构决策检查表

新增能力或修改架构时，应回答：

1. 它属于 collection、detection、telemetry、response 中的哪一层？
2. 它如何被控制平面调整、版本化、确认和审计？策略如何回滚，可逆动作如何撤销，不可逆动作如何审批和补偿？
3. 它消耗多少 CPU、内存、磁盘、网络和云侧计算预算？
4. 它产生 Event、Signal、Evidence 还是 Incident，语义是否清楚？
5. 它应在端侧还是云侧运行，为什么？
6. 失败、断网、重试和重复输入时，结果是否稳定且可解释？
7. 当前实现、产品化中能力和规划能力是否被明确区分？

无法回答这些问题的功能不应进入主架构。
